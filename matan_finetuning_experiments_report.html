Hebrew Handwriting Recognition — Finetuning Experiments on the Matan Dataset

Technical report · Project: TrOCR_Hebrew · Prepared June 08, 2026

Author: cyttic  |  Status: three training experiments completed/in-progress, all unsuccessful by the same mechanism

1. Executive summary

We attempted to train a Hebrew handwriting-recognition model on a new dataset (“matan”, ~4,400 training line-images from multiple writers) by finetuning our in-house base model. Three experiments were run with progressively more conservative training schedules. All three failed in exactly the same way: the model’s training loss fell smoothly (it memorised the training examples), but its actual reading accuracy on held-out writers did not improve — character error rate (CER) remained pinned around 85–100% throughout, and word error rate (WER) stayed above 100%.

Bottom line. The result is consistent and now well understood. Our base model’s image–to–text “bridge” is initialised randomly and is data-hungry; the matan set (~4,400 lines) is too small to train that bridge from scratch, regardless of how the schedule is tuned. We bracketed the schedule from 0 → 4 → 20 epochs of “warm-up” training and obtained the same failure each time. This is not a software defect — the pipeline is validated (see §6) — it is a data-scale limitation with a clear, low-risk path forward (§7).

2. Background

The model is a TrOCR-style system: a visual encoder (a Vision Transformer that “looks” at the line image) connected to a text decoder (DictaBERT, a strong Hebrew language model that produces the characters). The two halves are joined by a learned component called cross-attention — the bridge that lets the text side “read” the picture.

Critically, in our base model this bridge is initialised with random values (the decoder was originally a fill-in-the-blank language model, never trained to read images). Training therefore has to learn the entire visual–to–text mapping from scratch, which requires a large amount of data. Our project documentation flags this explicitly: “the bottleneck is data scale, not the decoder.”

3. The dataset

The matan dataset is a set of Hebrew handwritten text-line images, each paired with its ground-truth transcription. It was converted to the standard training format and split by writer (so no writer’s handwriting appears in both the training and the test portions — this prevents the model from “cheating” and gives an honest measure of whether it can read a new person’s handwriting). The training portion contains roughly 4,400 line-images; the held-out test portion ~900 lines, on which CER and WER are reported below.

4. How to read the numbers

Training loss
How well the model fits the training examples. Falling = it is learning something from the data it sees. Lower is better.
Validation loss
The same quantity measured on held-out data. If training loss falls while validation loss rises, the model is overfitting (memorising rather than generalising).
CER — Character Error Rate
Fraction of characters the model gets wrong on held-out test lines. The headline accuracy metric. 0.00 = perfect; ~0.90 = ~90% of characters wrong. A usable reader needs CER well under ~0.15 (15%).
WER — Word Error Rate
Same idea at the word level. A WER above 1.00 means the output needs more word edits than the reference even contains — i.e. the output is mostly garbage/insertions, not “close but imperfect.”

5. Experiments & results

Experiment 4  Failed

Configuration: finetune the base model on matan with the visual encoder unfrozen from epoch 1 (encoder + bridge + decoder all trained simultaneously). 8 epochs, batch size 16, learning rate 5×10-5.

Outcome: training loss fell from 4.60 to 0.82, but CER never dropped below ~0.86 and showed no downward trend; validation loss bottomed at epoch 5 and rose afterwards (overfitting). The best CER (0.80) occurred at epoch 2 — the model was not improving its reading over time.

Experiment 5  Failed

Hypothesis: exp 4 may have failed because unfreezing the encoder while the bridge was still random let noisy signals corrupt the encoder’s good visual features. Fix attempted: a staged schedule — first train with the encoder frozen (let the bridge stabilise against fixed, known-good visual features), then unfreeze.

Phase 1 (4 frozen epochs): training loss fell normally, but CER again stayed in the 0.90–1.08 band with no improvement — 4 epochs on ~4,400 lines was not enough exposure for the random bridge to begin reading.

Phase 2 (unfreeze): on unfreezing, validation loss and CER immediately moved the wrong way (CER 0.863 → 0.941 across two epochs while training loss fell). This matched the exp 4 failure and the run was stopped early to avoid wasting GPU time.

Experiment 6  In progress — preliminary

Hypothesis: perhaps the frozen warm-up simply needed to be much longer. Fix attempted: increase the frozen phase five-fold — 20 frozen epochs before unfreezing (then 10 unfrozen), batch size 16, learning rate 5×10-5.

Outcome (through epoch 15 of 20): the same pattern, now over a much longer run. Training loss fell steadily from 5.93 to 0.71; validation loss bottomed at epoch 5 (1.78) and has since risen to 2.04 (overfitting); and CER has no downward trend at all — its best value (0.81) was at epoch 1, and it has bounced in the 0.85–1.08 band ever since. WER has stayed above 1.0 throughout.

Reading these two charts together is the entire story: the loss chart (left) collapses toward zero — the model is clearly learning to fit its training data — while the error-rate chart (right) is essentially flat — that learning never translates into reading the image. The model lowers its loss by leaning on the decoder’s Hebrew-language knowledge and memorising training lines, not by grounding on the picture.

Cross-experiment comparison

Plotting CER for all three runs on one axis shows the schedule was bracketed from 0 to 20 frozen epochs with no effect — none of the runs comes remotely close to the accuracy a usable reader requires.

6. Why this happened (root cause)

The three experiments form a controlled sweep of a single variable — how long the model trains before (or whether) the encoder is unfrozen — and they all fail identically. That rules out the schedule as the cause and points to the underlying constraint:

  • The image–to–text bridge starts as pure noise and must be learned entirely from the training data.
  • ~4,400 lines is too little data to teach that bridge to “see” from scratch. For comparison, our successful pretraining run (§6.1) used roughly 125,000 synthetic lines — about 30× more data.
  • With insufficient data, the model takes the path of least resistance: it drives the loss down by memorising the training set and leaning on the decoder’s built-in Hebrew language knowledge, which improves the loss number without ever learning to read the actual handwriting — hence falling loss but flat, high CER, rising validation loss, and WER above 1.0.

6.1 Context — what success looks like

The pipeline itself is proven. The same model, trained on our large synthetic Hebrew dataset (~125,000 lines), reaches CER ≈ 0.06 (6%) and WER ≈ 0.15 on its test set — i.e. a genuinely working reader. The matan experiments fail not because the method is wrong, but because ~4,400 real lines cannot, on their own, train the randomly initialised bridge that the synthetic data successfully trained.

7. Conclusion & recommendation

Training a model on the matan dataset from the randomly initialised base is not viable at the current data scale, and further schedule tuning is not worth additional GPU budget — the 0 / 4 / 20-epoch bracket has settled the question.

Recommended next step (low-risk, follows the validated recipe):

  1. Warm-start from the synthetic-pretrained model (cyttic/trocr-hebrew-synthetic-cont) instead of the randomly initialised base. Its bridge is already trained on 125k synthetic lines, so finetuning on matan becomes a domain-adaptation task (adjusting a working reader to new handwriting) rather than teaching a blind model to see from 4,400 examples. This is the project’s documented recipe (synthetic pretrain → real finetune).
  2. If a from-base run is still required, the alternative is to add data to the frozen warm-up — mix the synthetic and/or existing human set in alongside matan — rather than adding more epochs over the same small set.

Either path addresses the actual constraint (data scale for the random bridge) rather than the schedule, which has been shown not to matter here.
